# **Чё, куда и для чего?**

* **Методология**;

  * Вызов вредоносного ответа от внутреннего сервера - если входные данные отражаются в ответе сервера без надлежащей очистки или используются для динамической генерации других данных.

## Использование отравления веб-кэша для доставки атаки XSS

> Когда неключевой ввод отражается в кэшируемом ответе без надлежащей очистки.
```python
GET /en?region=uk HTTP/1.1
Host: website.com
X-Forwarded-Host: a."><script>alert(1)</script>"

HTTP/1.1 200 OK
Cache-Control: public
<meta property="og:image" content="https://a."><script>alert(1)</script>"/cms/social.png" />
```

## Использование отравления веб-кэша для эксплуатации небезопасной обработки импорта ресурсов

> Неключевые заголовки используются для динамической генерации URL-адресов и импорта ресурсов, таких как внешние размещенные файлы JavaScript. Если изменить значение соответствующего заголовка на подконтрольный домен, потенциально можно манипулировать URL-адресом, чтобы он указывал на свой собственный вредоносный файл JavaScript.
```python
GET / HTTP/1.1
Host: innocent-website.com
X-Forwarded-Host: evil-user.net
User-Agent: Mozilla/5.0 Firefox/57.0

HTTP/1.1 200 OK
<script src="https://evil-user.net/static/analytics.js"></script>
```

## Использование отравления веб-кэша для эксплуатации уязвимостей обработки файлов cookie

> Файлы cookie часто используются для динамической генерации контента в ответе. Типичным примером может служить файл cookie, который указывает предпочитаемый пользователем язык, который затем используется для загрузки соответствующей версии страницы.
```python
GET /blog/post.php?mobile=1 HTTP/1.1
Host: innocent-website.com
User-Agent: Mozilla/5.0 Firefox/57.0
Cookie: language=pl;
Connection: close
```

## Использование нескольких заголовков для эксплуатации уязвимостей отравления веб-кэша

> веб-сайт требует безопасного соединения с использованием HTTPS. Чтобы обеспечить это, если получен запрос, который использует другой протокол, веб-сайт динамически генерирует перенаправление на себя, который использует HTTPS.
```python
GET /random HTTP/1.1
Host: innocent-site.com
X-Forwarded-Proto: http

HTTP/1.1 301 moved permanently
Location: https://innocent-site.com/random


X-Forwarded-Scheme: nothttps
X-Forwarded-Host: my-site.com
```
* `X-Forwarded-Proto` - стандартный заголовок для определения протокола (HTTP или HTTPS), который клиент использовал для подключения к прокси или балансировщику нагрузки. Журналы доступа к серверу содержат протокол, используемый между сервером и балансиром нагрузки, но не протокол, используемый между клиентом и балансировщиком нагрузки.
* `X-Forwarded-Scheme` - сообщает серверу, по какому протоколу (HTTP или HTTPS) изначально обращался клиент, прежде чем запрос прошёл через прокси-сервер или балансировщик нагрузки.
* `X-Forwarded-Host` - стандартный заголовком для идентификации первоначального хоста, запрошенного клиентом в Host Заголовок запроса HTTP.

## Использование ответов, которые раскрывают слишком много информации

* **Директивы управления кэшем**
> Одним из таких примеров является ситуация, когда ответы содержат информацию о том, как часто очищается кэш или насколько старым является текущий кэшированный ответ. Позволяет тщательно рассчитать время для одного вредоносного запроса, чтобы отравить кэш.

* **Заголовок Vary**
> определяет список дополнительных заголовков, которые следует рассматривать как часть ключа кэша, даже если они обычно не имеют ключа.

# Использование недостатков реализации кэша

## Ключевые недостатки кэша

* Многие веб-сайты и CDN выполняют различные преобразования ключевых компонентов, когда они сохраняются в ключе кэша.
  * Исключение строки запроса
  * Фильтрация определенных параметров запроса
  * Нормализация ввода в ключевых компонентах

Эти преобразования могут привести к расхождениям между данными, которые записаны в ключ кэша, и данными, которые передаются в код приложения, хотя все они исходят из одного и того же ввода. 

## Методология проверки кэша

* **Определение подходящего оракула кэша**

> Оракул кэша — это просто страница или конечная точка, которая предоставляет обратную связь о поведении кэша. Она должна быть кэшируемой и должна каким-то образом указывать, кэшированный это ответ или он пришел напрямую с сервера.

На это может указывать:
* HTTP-заголовок
* Наблюдаемые изменения в динамическом контенте
* Различные времена ответа
* обратиться к соответствующей документации

В идеале кэш-оракул также будет отражать весь URL и по крайней мере один параметр запроса в ответе. 

> Например, веб-сайты на базе Akamai могут поддерживать заголовок Pragma: akamai-x-get-cache-key, который можно использовать для отображения ключа кэша в заголовках ответа:
```python
GET /?param=1 HTTP/1.1
Host: website.com
Pragma: akamai-x-get-cache-key

HTTP/1.1 200 OK
X-Cache-Key: website.com/?param=1
```
* **Проверка обработки ключа**

Следующий шаг — выяснить, выполняет ли кэш дополнительную обработку входных данных при генерации ключа кэша. 

> Исключается ли что-либо из ключевого компонента при его добавлении в ключ кэша? Обычными примерами являются исключение определенных параметров запроса или даже всей строки запроса и удаление порта из заголовка Host. При  прямо доступе к ключу кэша, можно просто сравнить ключ после внедрения различных входных данных. 

Домашняя страница целевого сайта автоматически перенаправляет пользователей на страницу, специфичную для региона. Использует заголовок Host для динамической генерации заголовка Location в ответе:
```python
GET / HTTP/1.1
Host: website.com

HTTP/1.1 302 Moved Permanently
Location: https://website.com/en
Cache-Status: miss
```
Чтобы проверить, исключен ли порт из ключа кэша, нужно запросить произвольный порт и убедиться, что получен свежий ответ от сервера, который отражает эти входные данные:
```python
GET / HTTP/1.1
Host: website.com:9999

HTTP/1.1 302 Moved Permanently
Location: https://website.com:9999/en
Cache-Status: miss
```

Отправить еще один запрос, но без указания порта:
```python
GET / HTTP/1.1
Host: website.com

HTTP/1.1 302 Moved Permanently
Location: https://website.com:9999/en
Cache-Status: hit
```
Это доказывает, что порт исключается из ключа кэша но полный заголовок все равно передается в код приложения и отражается в ответе.

* **Определить эксплуатируемый гаджет**

> Часто это будут классические уязвимости на стороне клиента, такие как отраженный XSS и открытые перенаправления. 

## Эксплуатация недостатков ключа кэша

* **Неключевой порт**

> URL-адрес перенаправления был динамически сгенерирован на основе заголовка Host. Это может позволить создать атаку типа «отказ в обслуживании», просто добавив произвольный порт к запросу. Все пользователи, которые просматривали домашнюю страницу, будут перенаправлены на недействительный порт, фактически отключая домашнюю страницу до истечения срока действия кэша. Если сайт позволяет указать нечисловой порт можно попытать счастье с XSS.
______________________
* **Неключевая строка запроса**

> Как и заголовок Host, строка запроса обычно имеет ключ. Однако одно из наиболее распространенных преобразований кэш-ключа — исключить всю строку запроса.

* *Обнаружение неключевой строки запроса*

Иногда отсутствие явного сообщения о кэшировании заставляет динамические страницы выглядеть так, как будто они полностью статические.

> Чтобы определить динамическую страницу, необходимо наблюдать как изменение значения параметра влияет на ответ. Но если строка запроса не имеет ключа, большую часть времени буду получать `HIT`, а значит, и неизменный ответ, независимо от любых добавленных параметров. Очевидно, что это также делает классические параметры запроса Cache-Buster избыточными.

Альтернативные способы добавления блокировки кэша которые не мешают поведению приложения
```python
Accept-Encoding: gzip, deflate, cachebuster
Accept: */*, text/cachebuster
Cookie: cachebuster=1
Origin: https://cachebuster.website.com

Param Miner - Add static/dynamic cache buster and Include cache busters in headers
```
Другой подход — посмотреть, есть ли какие-либо расхождения между тем, как кэш и бэкэнд нормализуют путь запроса. Отправлять запросы с разными ключами, которые по-прежнему попадают в одну и ту же конечную точку.
```python
Apache: GET //
Nginx: GET /%2F
PHP: GET /index.php/xyz
.NET GET /(A(xyz)/
```
* *Использование строки запроса без ключа*

> Исключение строки запроса из ключа кэша может фактически сделать отраженные уязвимости XSS еще более серьезными.
________________________
* **Неключевые параметры запроса**

> Некоторые веб-сайты исключают только определенные параметры запроса, которые не имеют отношения к внутреннему приложению, например параметры для аналитики или обслуживания целевой рекламы. Параметры UTM, такие как utm_content, являются хорошими кандидатами для проверки во время тестирования.
________________________
* **Скрытие параметра кэша**

> Любые расхождения в анализе между кэшем и приложением могут потенциально позволить внедрить произвольные параметры в логику приложения, «скрыв» их в исключенном параметре. Фактическим стандартом является то, что параметру будет либо предшествовать вопросительный знак `?`, если он первый в строке запроса, либо амперсанд `&`. Некоторые плохо написанные алгоритмы анализа будут обрабатывать любые `?` как начало нового параметра, независимо от того, первый он или нет.
```html
GET /?example=123?excluded_param=bad
```
В этом случае кэш идентифицирует два параметры и исключает второй из ключа кэша. Однако сервер не принимает второй `?` в качестве разделителя и вместо этого видит только один параметр, `example`, значением которого является вся остальная часть строки запроса, включая полезную нагрузку.

* *Эксплуатация особенностей анализа параметров*

> Подобные проблемы сокрытия параметров могут возникнуть когда бэкэнд определяет отдельные параметры, которые кэш не определяет. Например, фреймворк Ruby on Rails интерпретирует как амперсанд `&`, так и точку с запятой `;` как разделители. При использовании в сочетании с кэшем, который этого не допускает, потенциально можно использовать другую особенность, чтобы переопределить значение ключевого параметра в логике приложения.

```html
GET /?keyed_param=abc&excluded_param=123;keyed_param=bad-stuff-here
```
Как следует из названий, `keyed_param` включен в ключ кэша, а `exclude_param` — нет. Многие кэши будут интерпретировать это только как два параметра, разделенных амперсандом:
```html
1. keyed_param=abc
2. excepted_param=123;keyed_param=bad-stuff-here
```
После того, как алгоритм анализа удалит exclude_param, ключ кэша будет содержать только keyed_param=abc. Однако на бэкенде Ruby on Rails видит точку с запятой и разбивает строку запроса на три отдельных параметра:
```html
1. keyed_param=abc
2. excepted_param=123
3. keyed_param=bad-stuff-here
```
> Если есть дублирующиеся параметры, каждый из которых имеет разные значения, Ruby on Rails отдает приоритет последнему вхождению. Конечный результат заключается в том, что ключ кэша содержит невинное, ожидаемое значение параметра, что позволяет обслуживать кэшированный ответ как обычно для других пользователей. Однако на внутреннем уровне тот же параметр имеет совершенно другое значение, которое является внедренной полезной нагрузкой. 

Если веб-сайт использует `JSONP` для выполнения междоменного запроса, он часто будет содержать параметр обратного вызова для выполнения заданной функции для возвращаемых данных: `GET /jsonp?callback=innocentFunction` эти методы можно использовать чтобы переопределить ожидаемую функцию обратного вызова и вместо этого выполнить произвольный JavaScript
________________________
* **Использование поддержки fat GET**

> В некоторых случаях метод HTTP может не быть ключом. Это может позволить отравить кэш запросом POST, содержащим вредоносную полезную нагрузку в теле и она будет обслуживаться в ответ на запросы GET пользователей. Хотя этот сценарий довольно редок, иногда можно достичь похожего эффекта, просто добавив тело к запросу GET, чтобы создать `толстый` запрос GET
```python
GET /?param=innocent HTTP/1.1
…
param=bad-stuff-here
```
В этом случае ключ кэша будет основан на строке запроса, но значение параметра на стороне сервера будет взято из тела.

Это возможно только в том случае, если веб-сайт принимает запросы GET, имеющие тело, но есть потенциальные обходные пути. 

* Переопределение метода HTTP:
```python
GET /?param=innocent HTTP/1.1
Хост: website.com
X-HTTP-Method-Override: POST
…
param=bad-stuff-here
```
> Пока заголовок `X-HTTP-Method-Override` не имеет ключа, можно отправить запрос псевдо-POST, сохранив ключ кэша GET, полученный из строки запроса.
________________________
* **Использование динамического контента при импорте ресурсов**

> Импортированные файлы ресурсов обычно статичны, но некоторые отражают ввод из строки запроса. Это в основном считается безвредным, поскольку браузеры редко выполняют эти файлы при прямом просмотре, и пользователь не имеет контроля над URL-адресами, используемыми для загрузки подресурсов страницы. Однако, комбинируя это с отравлением веб-кэша, можно внедрять контент в файл ресурсов.
```python
GET /style.css?excluded_param=123);@import… HTTP/1.1

HTTP/1.1 200 OK
…
@import url(/site/home/index.part1.8a6715a2.css?excluded_param=123);@import…
```
Это поведение можно использовать для внедрения вредоносного CSS, который извлекает конфиденциальную информацию из любых страниц, которые импортируют `/style.css`.

> Если на странице, импортирующей файл CSS, не указан `DOCTYPE`, можно даже использовать статические файлы CSS. При правильной настройке браузеры просто прочесывают документ в поисках CSS, а затем выполняют его. Это означает, что иногда можно отравлять статические файлы CSS, вызывая ошибку сервера, которая отражает исключенный параметр запроса.
```python
GET /style.css?excluded_param=alert(1)%0A{}*{color:red;} HTTP/1.1

HTTP/1.1 200 OK
Content-Type: text/html
…
This request was blocked due to…alert(1){}*{color:red;}
```
________________________

* **Нормализованные ключи кэша**

> Любая нормализация, применяемая к ключу кэша, также может привести к эксплуатируемому поведению. Например, отраженный XSS в параметре, на практике его часто невозможно эксплуатировать. Это происходит потому, что современные браузеры обычно кодируют URL-адреса необходимых символов при отправке запроса, а сервер не декодирует их. Ответ, который получает предполагаемая жертва, будет содержать просто безвредную строку в кодировке URL-адреса.

Некоторые реализации кэширования нормализуют ввод с ключом при добавлении его к ключу кэша.
```html
GET /example?param="><test>
GET /example?param=%22%3e%3ctest%3e
```
Если отправить вредоносный запрос с помощью Burp Repeater, можно отравить кэш незакодированной полезной нагрузкой XSS. Когда жертва посещает вредоносный URL, полезная нагрузка все равно будет закодирована в URL ее браузером; однако после нормализации URL кэшем он будет иметь тот же ключ кэша, что и ответ, содержащий вашу незакодированную полезную нагрузку.
_______________________
* **Внедрение ключа кэша**

> Компоненты, учитываемые в ключе, часто объединяются в строку для формирования ключа кеша. Если кеш не реализует правильное экранирование разделителей между компонентами, потенциально можно использовать это поведение, чтобы сформировать два разных запроса с одинаковым ключом кеша.

В следующем примере для разделения различных компонентов в ключе кеша используются двойные подчёркивания (__), и они не экранируются. Вы можете использовать это, сначала отравив кеш запросом, содержащим вашу полезную нагрузку в соответствующем ключевом заголовке:
```html
GET /path?param=123 HTTP/1.1
Origin: '-alert(1)-'__

HTTP/1.1 200 OK
X-Cache-Key: /path?param=123__Origin='-alert(1)-'__

<script>…'-alert(1)-'…</script>
```
Если затем заставить пользователя посетить следующий URL, ему будет выдан отравленный ответ:
```html
GET /path?param=123__Origin='-alert(1)-'__ HTTP/1.1

HTTP/1.1 200 OK
X-Cache-Key: /path?param=123__Origin='-alert(1)-'__
X-Cache: hit

<script>…'-alert(1)-'…</script>
```

## Отравление внутренних кэшей

> Вместо того чтобы кэшировать ответы целиком, некоторые из кэшей разбивают ответ на повторно используемые фрагменты и кэшируют их каждый по отдельности. Например, фрагмент для импорта широко используемого ресурса может храниться как отдельная запись кэша. Затем пользователи могут получить ответ, состоящий из смеси контента с сервера, а также нескольких отдельных фрагментов из кэша. Поскольку эти кэшированные фрагменты предназначены для повторного использования в нескольких различных ответах, концепция ключа кэша на самом деле не применяется.

* **Как определить внутренние кэши**

> Одной из проблем, связанных с интегрированными кэшами уровня приложений, является то, что их может быть трудно определить и исследовать, поскольку часто отсутствует обратная связь с пользователем.
Если ответ отражает смесь ввода из последнего отправленного запроса и ввода из предыдущего запроса, это ключевой показатель того, что кэш хранит фрагменты, а не целые ответы. То же самое применимо, если ввод отражается в ответах на нескольких отдельных страницах, в частности на страницах, на которых никогда не пытался внедрить свой ввод.

# Как предотвратить уязвимости отравления веб-кэша

* Полностью отключить кэширование. **Directed by Robert B.Weide** 
* Ограничение его чисто статическими ответами также эффективно, при условии, что достаточно осторожны с тем, что классифицируется как «статическое». Например, убедись, что злоумышленник не может обмануть внутренний сервер, заставив его получить свою вредоносную версию статического ресурса вместо подлинного.

* Способы митигации:
 * При рассмотрении возможности исключения чего-либо из ключа кэша по соображениям производительности, вместо этого переписать запрос.
 * Не принимать толстые запросы GET. Некоторые сторонние технологии могут разрешать это по умолчанию.
 * Исправить уязвимость на стороне клиента, даже если они кажутся неэксплуатируемыми.
